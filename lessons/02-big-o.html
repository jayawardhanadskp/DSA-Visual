Big-O: how fast is my code?

Big-O answers one question: when the input gets 10× bigger, how much more work does my code do? It's how you compare two solutions without a stopwatch, and how you know before coding whether your idea is fast enough.

🎯 After this lesson you can
  • look at code and say its time and space complexity
  • know the cost of common Python operations (and spot "hidden loops")
  • read LeetCode's limits (like n ≤ 10⁵) and know which complexity you need

1. The idea: count steps, not seconds

Seconds depend on your laptop. Steps don't. Big-O counts how the number of steps grows with the input size n, and keeps only the part that matters when n is big. Watch the three most common shapes:

O(n) — linear

Searching an unsorted list: in the worst case (target at the end, or missing) we look at every element once. 6 elements → 6 steps. 1 million elements → 1 million steps.

O(n²) — quadratic

A loop inside a loop over the same list. For every i, the inner loop runs n times. 4 elements → 16 steps. 1,000 elements → 1,000,000 steps.

O(log n) — logarithmic

Halve the problem every step. 64 → 32 → 16 → 8 → 4 → 2 → 1 is 6 steps. 1,000,000 needs only 19 steps! This is why binary search (lesson 12) is so fast. log₂(n) just means "how many times can I halve n until I reach 1?"

Why we drop constants 2n and n both grow the same way: double the input → double the work. n² is a different way: double the input → 4× the work. Big-O cares about the shape of growth. (In real life constants still matter a bit — but first get the shape right.)

4. Space complexity

Same idea for memory: how much extra memory does the code use as n grows?

  • A few variables (counters, pointers) → O(1) space.
  • A new list/set/dict that can hold up to n items → O(n) space.
  • An n × n grid → O(n²) space.
  • Recursion uses the call stack: recursion depth d → O(d) space (lesson 10).

Very often you trade one for the other: use O(n) memory (a set) to go from O(n²) time to O(n) time. You'll do exactly that in the practice below.

6. The LeetCode trick: read the constraints

Every LeetCode problem lists limits like 1 <= nums.length <= 10^5. A Python solution can do roughly 10⁷ simple steps in time. So the limit tells you which complexity they expect — before you even think about the algorithm:

n is at most…you can afford…think about…
10–12O(n!)all permutations, backtracking
20–25O(2ⁿ)all subsets, backtracking
~500O(n³)three nested loops, some DP
~5,000O(n²)all pairs, 2-D DP
~10⁵–10⁶O(n log n) or O(n)sorting, heap, hashing, two pointers, sliding window, binary search
bigger (10⁹, 10¹²)O(log n) or O(1)binary search on the answer, math

8. 📌 Summary

  • Big-O = how the work grows with n. Count loops: sequence adds, nesting multiplies, halving gives log n. Drop constants.
  • Know the hidden costs: in on a list, pop(0), insert(0, …), slicing, string +=.
  • Trading memory for time (a set or dict) is the most common speed-up in DSA.
  • From now on, after every solution, say: "time O(…), space O(…)".
